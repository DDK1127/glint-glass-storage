# 一次送出一批真實請求（batch）：queue 與 cache（2026-10-19）

設定：`experiments/batch-story/config.json`；腳本：`scripts/run_batch_story.py`、`scripts/plot_batch_story.py`、`scripts/probes/batch_fetch_first.py`（`.venv/bin/python`）。圖：`fig_batch_gap.png`（英文、300 dpi）。

- 每個 batch 從 trace 的 10 分鐘區間（08–13 點，各一段）均勻抽 N 筆讀取，保留順序，**全部在 t=0 送出**。不拉長時間軸，也不需要定義負載。
- N = 500 / 1,000 / 2,000 / 4,000，主軸用 **2,000**。
- 1 個 reader、8 台 Zone 車、B1，6 個 batch 的中位數。

## 每個請求的讀取時間要設多少

Silica 論文：一個 track 是最小讀取單位（§5），約 O(100) + O(10) 個 sector，每個 sector 超過 100 kB（§3），所以一個 track 約 11 MB 以上；reader 速度是 30 MB/s 的倍數，介於 30–210 MB/s（§3）。讀一個 track 約 0.05–0.4 秒。原本的 1 秒偏高，**0.25 秒較貼近論文**，所以測 0.1 / 0.25 / 1 秒三組。

## 結果（batch 2,000 筆）

| 每個請求讀取時間 | 做法 | 完成時間（秒） | 比下限多 | reader 忙碌 | queue 是空的 |
|---|---|---:|---:|---:|---:|
| 0.1 秒 | 沒有 queue | 407 | 40% | 63% | 100% |
| | queue 8 格 | **318** | 9% | 74% | 30% |
| | queue + LRU cache | 317 | 9% | 80% | 24% |
| 0.25 秒 | 沒有 queue | 661 | 12% | 84% | 100% |
| | queue 8 格 | **617** | 4% | 89% | 14% |
| | queue + LRU cache | 617 | 4% | 90% | 13% |
| 1 秒 | 沒有 queue | 2,146 | 3% | 96% | 100% |
| | queue 8 格 | 2,117 | 1% | 97% | 5% |
| | queue + LRU cache | 2,117 | 1% | 97% | 5% |

一個 batch 只用到約 30 片玻璃。每片只被打開一次，那一次就把它所有的請求讀完：batch 2,000 時平均每片 66.7 個請求。

## 觀察

1. **在 batch 下，queue 的效益取決於讀取有多快。** 讀取 0.1 秒時，queue 把完成時間縮短 22%（407 → 318 秒）。讀取 1 秒時只縮短 1%，因為 reader 本來就 96% 在忙。
2. **原因**：沒有 queue 時，車要等 reader 空了才能交貨，搬運和讀取無法重疊。讀取越快，搬運的等待佔比越大，queue 讓兩者重疊的好處就越明顯。讀取慢時，reader 本身是瓶頸，重疊與否差不多。
3. **在 batch 下，cache 幾乎沒有作用**。所有請求一開始就知道，每片玻璃一次就讀完它所有的請求，不會再被要回來，cache 裡的玻璃沒有人用。唯一的小效果是：讀完的玻璃留在 cache 就不用馬上送回，車可以先做別的事（batch 500、0.1 秒時快 9%）。
4. **cache 的價值只出現在「請求陸續到達」的情況**：一片玻璃讀完送走後，又有新請求進來。這也是之前連續到達實驗中，cache 有正有負的原因。
5. **送回的先後（先送回或先搬）在 batch 下沒有差別**（`batch_fetch_first.py`：完成時間相差不到 0.2%）。
6. **batch 大小不改變上述結論**：batch 500 時趨勢相同，只是每片玻璃讀到的請求較少（17.2 個），queue 的效益略大（讀取 0.25 秒時 −6%）。

## 小結

- 一次送出一整批時，Silica 的「同一片的請求一起讀」已經把合併做到最好，每片只打開一次。剩下的改善空間只有「讓搬運和讀取重疊」，也就是 queue 的工作，大小取決於讀取速度。
- 要讓 cache 有意義，必須是請求持續到達、同一片玻璃會被重複要求的情況。

> 更新（同日）：這份結果用的是「每個請求固定讀取時間」的舊模型，以及抽樣出來的 batch。之後改用依 throughput 和 track 計算的讀取模型，batch 也改成「某個區間內的所有請求」，見 `results/batch-slo/`。

# 熱 platter 重複讀取分析（2026-10-19）

腳本：`scripts/analyze_vdi_reuse.py`。只分析 trace 的請求序列，以「間隔幾筆請求」計算，不受模擬的時間縮放影響。Fujitsu VDI LUN0 一小時，140 萬筆讀取。

| | contiguous | hash_1gib |
|---|---:|---:|
| 用到幾片 platter（共 640） | 503 | 635 |
| 前 5% 的 platter 佔全部讀取 | 37% | 24% |
| 前 10% 的 platter 佔全部讀取 | 51% | 38% |
| 再次讀取時，中間沒有讀過別片（緊接重複，合併就能處理） | 53% | 49% |
| 再次讀取在 10 筆請求內 | 82% | 77% |
| 再次讀取在 100 筆請求內 | 94% | 89% |
| LRU cache 留 C 片，扣除緊接重複後能多命中的讀取：C=2 | 16% | 15% |
| 同上 C=4 | 28% | 26% |
| 同上 C=8 | 36% | 33% |
| 同上 C=16 | 41% | 38% |
| 同上 C=64 | 45% | 45% |
| 一個窗口（2,000 筆）讀最多的 8 片，下一窗口仍被讀到 | 88% | 75% |
| 這 8 片佔下一窗口的讀取 | 49% | 21% |

觀察：

1. **讀取集中在少數 platter**：前 10% 的 platter 佔 38–51% 的讀取。
2. **重複讀取的間隔很短**：約一半是緊接重複（合併可處理）。其餘大多在 100 筆請求內又回來。
3. **小 cache 就有效果，而且很快飽和**：在合併之外，留 8 片可多命中約三分之一的讀取，留 16 片約四成，再大收益很小。
4. **熱度會延續**：這一窗口最熱的 8 片，下一窗口有 75–88% 仍被讀到。用「最近一段時間的讀取次數」判斷熱 platter 是可行的。

**重要限制：platter 容量**。Silica 每片 platter 可存「multiple TBs」（SOSP'23 §3）。這個 LUN 的位址範圍約 4.7 TB，在真實容量下只需 1–2 片。目前把它攤到 640 片（每片約 7.4 GiB），等於把容量縮小了數百倍。所以上述數字描述的是「位址空間按比例縮小後」的局部性，不是真實 platter 的重複率。這一點必須先討論。

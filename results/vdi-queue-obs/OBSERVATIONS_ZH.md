# 真實 trace 下的 Queue 觀察（2026-10-19）

設定見 `experiments/vdi-queue-obs/config.json`，腳本 `scripts/run_vdi_queue_obs.py`（用 `.venv/bin/python`）。

- **負載**：只用 Fujitsu 企業 VDI trace（Lee et al., SYSTOR'17；`data/2016022211-LUN0.csv`，與 GAIA 同一資料集）的讀取。請求順序和大小完全取自 trace，沒有合成負載。
- **系統**：1 個 reader、8 台 Zone shuttle，排程為 Silica 的做法（B1：最早排隊的 platter 優先，同片請求合併）。
- **資料擺放**：trace 沒有 platter 位置，所以做兩種：
  - `contiguous`：依位址連續擺放，保留局部性。
  - `hash_1gib`：每 1 GiB 隨機擺放，沒有局部性。
- **到達方式**：
  - 突發：20 個窗口，每個窗口取 400 筆連續讀取，全部在 t=0 到達。
  - 連續：6 個窗口，每個窗口 2,000 筆。把 trace 的時間軸拉長，讓平均到達率等於 B1 吞吐量的 50% / 75% / 90%，保留原本的突發形狀。
- 表中為中位數。

## 觀察

1. **主要的浪費來自 Zone 把請求佇列切碎。** 突發時，reader 的空等有 84–98% 發生在尾段：一半的車已經沒有自己區的工作，剩下的工作集中在少數幾區。
2. **連續到達時也一樣，不是突發造成的假象。** 即使負載 90%，仍有 18–43% 的車時間是「別區有工作、自己卻閒著」，同時 reader 有 18–31% 的時間在空等。
3. **沒有局部性時也會發生。** 在 hash_1gib（資料完全隨機擺放）下，最忙一區仍做了 20% 的趟數（平均是 12.5%），車有 17–27% 的時間在「別區有工作卻閒著」。這是隨機波動造成的，不需要熱區。有局部性的 contiguous 更嚴重（42%、39–49%）。
4. **合併很重要，而且讓工作變得「一塊一塊」。** 真實 trace 的位址局部性很強，每趟平均合併 7–15 個請求。推測：合併後每片 platter 的工作量大小不一，讓各區的工作更不均。**尚未驗證。**
5. **reader 入口的堵塞在這份 trace 中不明顯**（車只有 2–7% 的時間在入口等）。VDI 的讀取最大只有 200 KiB，沒有大檔，所以之前合成負載看到的「大檔凍結搬運」在這裡不會出現。

## 限制

- 只用了一個 LUN、一小時的 trace。
- 擺放方式是假設，所以兩種都報告。
- 時間軸是拉長的，負載是相對於 B1 吞吐量的比例。
- VDI 是虛擬桌面的主要儲存，不是備份系統，只取它的請求順序、大小和局部性。

- 每片 platter 平均被來回搬 2–3 次，同一片很快又被要求。
- 歸還佔了將近一半的搬運。
- buffer 和車大部分時間都有空。
- 最忙那一區的工作，七到八成是重複搬同幾片。
- 「秒數」依時間軸拉長的比例而定，之後應改用「間隔幾筆請求」表示。
